WHAT THIS IS
------------

The third module query contract, after IInventoryAvailability and IPartnerDirectory.

Until now, putting a part on a document meant sending the part id AND typing its SKU, its
description and its unit alongside. Three chances to disagree with the catalogue on every
line, on a document that is kept for years. The caller already knows which part it means -
it is sending the id - so it should not also have to say what that part is called.

    ICatalogDirectory   what is this part, and may we still trade it

Three questions: by id, by several ids at once, and by SKU - because nobody at a trade
counter types a GUID, they read the code off the bin label.

The values are still snapshotted onto the document. A part renamed in 2027 must not silently
rewrite an order confirmed in 2026. This is where the snapshot is TAKEN, not a replacement
for taking one.

PartDescriptor carries no money. Whether a core deposit is owed is a fact about the part and
it is in there; what it costs is not, because an amount would drag a currency and a rounding
policy across the boundary and the contract would stop being flat.


WHAT IT CLOSES
--------------

1. Three commands lost their SKU, description and unit parameters:

       AddSalesOrderLineCommand
       AddPurchaseOrderLineCommand
       AddSuggestionToPurchaseOrderCommand

   All three now send only the part, the quantity and the price. An old client still sending
   the other three gets them silently ignored - worth knowing if you have anything scripted.

2. The unit is now always the part's stocking unit.
   Not a unit the caller chose. Every quantity ever recorded against a part is in that unit,
   so a line raised in another one was a reservation that could not be filled and an invoice
   that could not be reconciled. That whole class of mismatch is now unreachable through
   these three paths.

3. Sales refuses a part that is not sellable; Purchasing refuses one that is not purchasable.
   Deliberately different rules: a discontinued part is still sold down off the shelf, but
   ordering more of it is how dead stock gets bought on purpose. Where the catalogue knows
   what replaces a part, the refusal says so.

4. The reorder-point path goes through the same gate.
   A suggestion raised weeks ago against a part since withdrawn from purchasing used to roll
   straight onto an order. Two ways onto the same document that describe a part differently
   is how the same part ends up as "Brake pad set" on one order and "brk pads frt" on the next.


VERIFIED HERE / NOT VERIFIED HERE
---------------------------------

Compiled clean: ModuleContracts, and the Catalog, Sales and Purchasing Domain and Application
projects. Ran the eight new handler tests plus the status-list checks against the real domain
and handlers here - 12 checks, all passing.

Not compiled here: Catalog.Infrastructure, the Presentation projects, the Api, and the test
projects (no NuGet in the sandbox).

Checked by hand across the whole repo: no caller, test or sample still passes SKU, description
or unit to any of the three commands; no duplicate error codes; no module references another
module; every command handler is Scoped and the outbox creates its own scope, so the new
dependency cannot be resolved outside one; the by-SKU and Contains query shapes match ones
already running in your build.

The EF projection was rewritten to project into an anonymous type and map afterwards, which is
the shape CatalogReadStore and InventoryAvailability already use. It was briefly projecting
straight into a named record via its constructor - probably fine, but not a thing I could test
here, and not worth being clever about in the one place another module reaches into this one.


KNOWN LIMITS
------------

1. The lookup reads, it does not lock. A part discontinued between the lookup and the save is
   still added. Milliseconds wide, and the same trade-off as the other two contracts.

2. Prices are still typed by hand, on all three paths. Pricing is its own module and does not
   exist yet.

3. FindBySkuAsync is on the contract but nothing calls it yet. It is there because the counter
   screen will need it and the alternative is Sales holding its own SKU index.
